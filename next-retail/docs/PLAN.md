## Зачем этот документ

Арома ERP переписывается с нуля как веб-сервис: один проект на Next.js + TypeScript + Ant Design, SQLite на VPS, вход по логину и паролю. Python, локальный запуск на Windows и старый интерфейс в `static/` уходят.

Текущий код не выбрасываем вслепую: в нём уже правильно продуманы деньги, склад и правила владельца. Новый проект переносит эту логику по смыслу, а не построчно.

**Для ИИ-агента (Codex и др.):**

1. Прочитай документ целиком до первой строки кода.
2. Работай строго по этапам из раздела «План по этапам». Следующий этап начинай только после того, как выполнены все критерии приёмки текущего.
3. Логику бери из старого репозитория (файлы указаны в каждом разделе), но не копируй его стиль: длинные строки, однобуквенные имена, по несколько операторов в одной строке.
4. Если правило из этого документа противоречит старому коду, прав документ. Если документ молчит, остановись и спроси владельца.
5. Финансовые формулы не меняй и не «улучшай». Переноси их один в один и докажи тестами.

**Правила кода:**

- `page.tsx` — Server Component: проверка роли и чтение данных. Весь Ant Design — в соседнем `XxxView.tsx` с `"use client"`. В Server Component antd не рендерится.
- Изменения данных — только через Server Actions, каждая в начале проверяет сессию и роль. Публичного REST API нет.
- Полное состояние базы в браузер не отдаём. Сейчас `/api/state` шлёт все товары, партии, документы и движения сразу. Каждая страница читает только нужное, списки — со страницами.
- Состояние таблиц и вкладок хранится в URL (`?page`, `?q`, `?tab`): переживает перезагрузку и пересылку ссылки.
- Формы создания и редактирования — отдельные страницы (`/x/new`, `/x/[id]/edit`). Модальные окна — для подтверждений и действий в одно-два поля (списание, отмена с причиной).
- Денежная арифметика — только через `src/domain/money`. Обычные `number`, `toFixed` и `Math.round` для денег запрещены. Запрет закрепить правилом ESLint.
- Форматирование — Prettier, строка до 100 символов, один оператор на строку. Осмысленные имена (`remainingCost`, а не `rc`). Переводы строк — LF.
- Секреты и рабочая база в Git не попадают; папка `data/` исключена из сборки (`outputFileTracingExcludes`).

## Модель данных

Схему таблиц сохраняем почти как есть: так старая база переносится без пересчётов. Новое — только пользователи, журнал действий и поле «кто сделал» в документах.

**Единицы хранения (не менять):**

- Деньги — целые копейки (`INTEGER`).
- Объём и количество парфюма — тысячные доли мл (1 мл = 1000). Штучные товары — штуки.
- Проценты и коэффициенты — десятичные строки (`"2.9"`, `"3"`), не числа с плавающей точкой.
- Расчёты, сохранённые в документе, — JSON-снимок на момент проведения. По текущим ценам не пересчитывается.
- Даты — ISO-строки. Новые записи пишем в UTC. Старые со смещением (`+05:00`) переводим в UTC при переносе. Дата продажи — календарный день `YYYY-MM-DD` без времени.

## Бизнес-правила, которые нельзя сломать

Все правила ниже взяты из действующего кода и переносятся без изменений. Каждое должно быть покрыто тестом. Если кажется, что формула ошибочна, агент не исправляет её, а спрашивает владельца.

### Округление и точность

- Промежуточные вычисления — 28 значащих цифр, округление «к ближайшему чётному» (так работает Python `Decimal` по умолчанию). Именно так настраивается `decimal.js`.
- «До копейки» — математическое округление (0,005 → 0,01).
- «Вверх до шага» — всегда в большую сторону: минимальная цена, рекомендованная цена, округленная себестоимость.
- Предельная скидка — всегда вниз до 0,01%, чтобы не перейти безопасную границу.
- Денежный ввод — не больше 2 знаков после запятой, от 0 до 100 000 000. Запятая и точка равнозначны. Объём — не больше 3 знаков.
- Старый код отдаёт числа строками с хвостовыми нулями (`"412.50"`). В тестах сравниваем значения, а не запись строки.

### Складские документы

1. **Любая операция — одна транзакция.** Ошибка на любом шаге отменяет всё. У каждой формы есть ключ запроса: повторная отправка той же формы возвращает уже созданный документ.
2. **Поступление** — для всех видов, кроме готовых распивов. Стоимость партии = округлённая до копейки (цена × количество) + доставка + допрасходы. Для флаконов и атомайзеров обязателен объём одной штуки.
3. **Стоимость того, что берём из партии.** Если забираем весь остаток — вся остаточная стоимость. Иначе — остаточная стоимость × взятое ÷ остаток, округление до копейки. Так сумма партии всегда сходится до нуля. Партию выбирает человек, автоматического FIFO нет.
4. **Вскрытие на распив** — из партии флаконов с известным объёмом. Полученный объём = объём флакона × штуки − потери (должен быть больше нуля). Стоимость парфюма = стоимость взятых флаконов. Карточка «парфюм в мл» создаётся один раз на флакон: код `ML-<код флакона>`, название флакона без хвоста «— ОБЪЁМ».
5. **Выпуск распивов.** Сначала расчёт выпуска (ниже) с отпечатком: SHA-256 от объёма, выбранных партий и составляющих стоимости. Если к моменту проведения отпечаток другой — отказ «Расчёт изменился». Списывается объём × штуки парфюма, столько же атомайзеров и наклеек (если выбраны). Стоимость партии распивов = сумма списаний + (работа + допрасходы) × штуки. Карточка распива одна на сочетание «парфюм + объём + атомайзер + наклейка», код `R-000001` по порядку.
6. **Списание** — только с причиной (по умолчанию «Пробник / тестер»).
7. **Отмена документа** — только с причиной и только для проведённого. Если товар из документа уже использован — отказ «сначала отмените связанные операции». Иначе полученная партия аннулируется, списанное возвращается в исходные партии с теми же суммами, создаётся документ «Отмена». Документы никогда не удаляются и не редактируются.

### Расчёт выпуска (из реальных партий)

- Объёмы — только 1, 2, 3, 5, 10 мл. Атомайзер не меньше объёма. Парфюма в партии достаточно хотя бы на одну штуку.
- Себестоимость = средняя цена мл партии × объём + средняя цена атомайзера + средняя цена наклейки + работа (за мл или за штуку, по настройке) + допрасходы.
- Рекомендованная цена = себестоимость × коэффициент объёма, вверх до шага округления. Для 1 мл коэффициента по умолчанию нет.
- Минимальная цена = себестоимость ÷ (1 − сумма процентов расходов), вверх до копейки.
- Настройки по умолчанию: работа 8 ₽ за мл; расходы «Продавцу» 10%, «Эквайринг» 3%, «Реклама» 5%, «Прочие» 2%; коэффициенты 2 мл — 3, 3 мл — 2,9, 5 мл — 2,8, 10 мл — 2,5; шаг 10 ₽.

### Калькулятор себестоимости, формула v3 (`perfume_markup_v3`)

Считается для каждого включённого объёма (1 мл включён всегда). Источник — `calculator_v3.py`.

1. Доставка: «бесплатно» = 0, «за штуку» = сумма, «за коробку» = сумма ÷ штук в коробке.
2. Цена мл парфюма = (закупка + доставка) ÷ (объём × (1 − потери ÷ 100)). Потери по умолчанию 2%. При флажке «округлять себестоимость» — вверх до рубля.
3. Атомайзер (кроме 1 мл): либо цена с доставкой как введена, либо закупка + доставка атомайзера, до копейки. У 1 мл атомайзера и наклейки нет.
4. Себестоимость = объём × (цена мл + работа за мл) + наклейка + атомайзер. При флажке — вверх до рубля, иначе до копейки.
5. Рекомендованная цена = (себестоимость − атомайзер) × коэффициент − атомайзер. При флажке «округлять цену» — вверх до шага. Отрицательный результат → цены нет, предупреждение. _Формула выглядит необычно, но в коде помечена как согласованная с владельцем. Переносится как есть, вопрос в конце документа._
6. Цена продажи = (своя цена или рекомендованная) × (1 − скидка ÷ 100), до копейки.
7. Расходы с продажи: «Продавцу» (по умолчанию 10%) и «Эквайринг» (3%), каждый отдельно до копейки.
8. Минимальная цена = себестоимость ÷ (1 − проценты), вверх до копейки. Затем прибавляем по копейке, пока «цена − себестоимость − округлённые расходы» меньше нуля.
9. Предельная скидка = (1 − минимальная ÷ базовая) × 100, вниз до 0,01%.
10. Остаток с продажи = цена − себестоимость − расходы; статус «убыток» / «ноль» / «плюс». Предупреждение, если цена за мл растёт с увеличением объёма.

Прежняя формула (`calculator_quote` + `discount_analysis` в `server.py`, вариант `base_ml_v2`) переносится один в один только если в рабочей базе есть сохранённые расчёты в ней. Новые расчёты в ней не создаются. Расчёт нельзя пересохранить в другой формуле — только как новую копию.

### Журнал продаж

- Журнал не списывает остатки. Связь со складом — отдельный будущий этап, в этот проект не входит.
- Документ: от 1 до 200 строк, количество целое от 1 до 100 000. У товара должны быть заполнены себестоимость и цена. Фактическая цена не выше прайсовой.
- Оплата у каждой строки своя: наличные или карта. Комиссия строки = выручка × тариф эквайринга, до копейки. У наличных комиссия 0. Последний тариф запоминается.
- Старые документы с одной оплатой на весь чек распределяют комиссию по строкам методом наибольших остатков. Это нужно только для чтения и выгрузки старых документов, новые так не создаются.
- Итоги: валовая прибыль = выручка − себестоимость; остаток = валовая − комиссия; маржа = валовая ÷ выручка; наценка = валовая ÷ себестоимость. Итоги есть по наличным и по карте.
- При сохранении сервер пересчитывает документ и сравнивает с тем, что видел человек. Если цены изменились — отказ «Пересчитайте».
- Исправление — только с причиной и с проверкой номера версии. Строки, которые уже были, сохраняют свои исходные себестоимость и прайсовую цену. Они меняются только явным исправлением, и тогда себестоимость помечается как ручная. Заменить товар в строке нельзя: удалить строку и добавить новую.
- Аннулирование — с причиной. Удаления нет. Каждая версия сохраняется целиком, любую можно открыть и выгрузить в Excel и Word.
- Если себестоимость строки взята из CSV, в интерфейсе и выгрузке есть пометка «предварительная себестоимость».

### Каталог и импорт

- Названия, цены и реквизиты берутся из CSV дословно. Никаких переименований, «нормализации» и автоматических объединений карточек.
- Импорт карточек не создаёт приход на склад.
- Простой CSV: колонки `NAME` / `EXTERNAL_CODE` или «Название» / «Код». Объём — из колонки или из конца названия («… 50 мл»). Кодировка UTF-8 или Windows-1251, разделитель «;», «,» или табуляция. До 5 МБ и 10 000 строк. Повтор кода в файле — ошибка. Сначала предпросмотр, потом применение.
- Импорт БИФИТ: группы только «Распив» и «Объёмы». Сопоставление с существующей карточкой — по ID БИФИТ, затем по коду с совпадением вида, названия и объёма. При конфликте кода новая карточка получает `BF-<код>` и попадает в отчёт. В режиме «заменить каталог» карточки, которых нет в файле, уходят в архив. Карточка с партиями останавливает импорт целиком. Прайс продаж обновляется, сохранённые документы продаж — нет.

### Места хранения и сверка

- Один центральный склад и любое число магазинов; у каждого — история версий.
- Остатки по местам и перемещения **не делаем**: это отдельный будущий этап после согласования.
- Сверка прайса продаж с каталогом только показывает расхождения (статусы: связано, проверить, не найдено, без связи, только на складе). Ничего сама не объединяет.

### Цены конкурентов

- Источники: Allure Parfum, Odekolon, Randewoo, Духи.рф. Gold Apple и Aroma-Butik не добавлять без нового решения владельца.
- Запросы — только HTTPS и только к хостам из списка. Перед запросом проверяем, что IP публичный: на VPS это защита от запросов во внутреннюю сеть. Таймаут и ограничение размера ответа.
- Различать «товара нет», «сетевая ошибка» и «сайт показал проверку на робота».
- Сопоставление с нашим ароматом: система предлагает кандидатов (до 24) с предупреждениями о другом издании или концентрации, человек подтверждает ссылку. Парсеры сайтов переносим по `competitors.py` (`parse`, `find_candidates`, `model_equal`) и покрываем тестами на сохранённых HTML-страницах.

## Авторизация и роли

Без входа не открывается ни одна страница и ни один файл, включая фото и выгрузки. Схема входа проверена на практике.

**Вход:**

- Логин и пароль. Пароль хранится только как bcrypt-хеш. Сессия — зашифрованная httpOnly-cookie (`iron-session`) с флагом `secure` в production. Секрет сессии — из `.env` на сервере.
- Второй фактор (TOTP-код из приложения-аутентификатора) **обязателен для владельца**: в системе закупочные цены и вся выручка. Для продавцов — по желанию.
- Вход и 2FA — отдельные route handlers под `/api/auth/`, не server actions. Иначе лимит nginx на частоту входа можно обойти.
- Защита от перебора: nginx — 6 попыток входа в минуту с IP. Приложение блокирует вход на 15 минут после 10 неудач на пару «логин + IP» или 30 неудач с одного IP. Счётчики хранятся в базе, владелец видит и снимает блокировки.
- Первый пользователь создаётся при первом запуске на пустой базе: логин `admin`, пароль из `INITIAL_ADMIN_PASSWORD` (случайный, его печатает скрипт настройки сервера). При первом входе система требует сменить пароль и настроить 2FA.
- Проверка прав — на сервере, в каждой странице и каждой server action. Скрытая кнопка в интерфейсе защитой не считается.
- Каждое изменение данных, входы и неудачные попытки пишутся в журнал действий. IP клиента берётся из `X-Forwarded-For`, который перезаписывает nginx.

**Роли (предложение, владелец подтверждает до этапа 2):**

| Раздел                                                 | Владелец (`owner`) | Продавец (`seller`)              |
| ------------------------------------------------------ | ------------------ | -------------------------------- |
| Журнал продаж: создать документ                        | да                 | да                               |
| Журнал продаж: исправить, аннулировать                 | да                 | только свои, в день продажи      |
| Себестоимость, закупочные цены, прибыль, маржа         | да                 | нет (поля не приходят в браузер) |
| Товары: просмотр и цены продажи                        | да                 | да                               |
| Товары: создание, изменение, импорт                    | да                 | нет                              |
| Склад: остатки (без сумм)                              | да                 | да                               |
| Склад: поступление, вскрытие, выпуск, списание, отмена | да                 | нет                              |
| Калькулятор, настройки расчёта, цены конкурентов       | да                 | нет                              |
| Пользователи, журнал действий, бэкапы                  | да                 | нет                              |

Если системой пользуется только владелец, роль `seller` всё равно закладывается в схему: потом не придётся переделывать проверки прав.

## Деплой на VPS

Сервер ничего не собирает. GitHub Actions проверяет и собирает релиз, отправляет архив по SSH, скрипт на сервере делает копию базы, переключает релиз и сам откатывается, если приложение не поднялось. Новый сервер настраивается одной командой с компьютера разработчика. Все скрипты агент пишет сам по этой спецификации.

Целевой сервер: Ubuntu 24.04 или новее (Debian 12 тоже подойдёт), x86-64, от 2 ГБ RAM, доступ по SSH под root или пользователем с sudo. Домен смотрит на IP сервера напрямую или через прокси Cloudflare.

### Раскладка на сервере

- `/opt/aroma/current` — симлинк на активный релиз. PM2 запускает приложение через него, поэтому перезапуск подхватывает новый релиз.
- `/opt/aroma/releases/<ГГГГММДД-ЧЧММСС>-<7 символов sha>/` — распакованные сборки, хранятся 5 последних.
- `/opt/aroma/shared/.env` — секреты и настройки, права 600: `SESSION_SECRET`, `DATABASE_PATH`, `PHOTOS_DIR`, `PORT`, `APP_TZ`, `INITIAL_ADMIN_PASSWORD`.
- `/opt/aroma/shared/data/aroma.db` — база SQLite в режиме WAL (рядом файлы `-wal` и `-shm`).
- `/opt/aroma/shared/data/photos/` — фото товаров.
- `/opt/aroma/shared/backups/` — копии базы перед деплоем и ночные.
- Всё принадлежит пользователю `deploy`: от него работает приложение и под ним заходит CI. Вход только по ключу, без пароля и без sudo.

### Файлы, которые создаёт агент

| Файл                           | Где выполняется        | Задача                                                        |
| ------------------------------ | ---------------------- | ------------------------------------------------------------- |
| `next.config.ts`               | сборка                 | Standalone-сборка, исключение `data/`, заголовки безопасности |
| `.nvmrc`                       | CI                     | Версия Node: 24                                               |
| `.github/workflows/deploy.yml` | GitHub Actions         | Проверки, сборка, упаковка, выкладка                          |
| `deploy/remote-deploy.sh`      | сервер, под `deploy`   | Активация релиза и автооткат                                  |
| `deploy/ecosystem.config.cjs`  | сервер, PM2            | Как запускать приложение                                      |
| `deploy/backup-db.sh`          | сервер, cron           | Ночная копия базы                                             |
| `deploy/setup-server.sh`       | сервер, под root       | Подготовка чистого сервера                                    |
| `deploy/nginx.conf.template`   | сервер                 | Шаблон конфига nginx                                          |
| `deploy/bootstrap.sh`          | компьютер разработчика | Новый сервер одной командой                                   |
| `src/instrumentation.ts`       | приложение при старте  | Миграции, первый пользователь, планировщик бэкапа в S3        |
| `DEPLOY.md`                    | для людей              | Как настроить, выкатить, откатить, восстановить               |

Общие требования к скриптам: bash в строгом режиме (остановка на первой ошибке и незаданной переменной), проверка `shellcheck` в CI. Вывод по-русски, шаги пронумерованы. `setup-server.sh` и `bootstrap.sh` можно безопасно запускать повторно: сделанное пропускается, база и `.env` никогда не перезаписываются.

### 1. Сборка для сервера

- `output: "standalone"`. Next кладёт в `.next/standalone` файл `server.js` и минимальный `node_modules` (около 20 МБ в архиве). Папки `public` и `.next/static` он туда **не копирует**: их докладывает шаг упаковки. Иначе сайт откроется без стилей и скриптов.
- Доступ к базе строится от `process.cwd()`. Из-за этого трассировка файлов тянет локальную `data/` в сборку. Исключить её через `outputFileTracingExcludes` для всех маршрутов.
- Заголовки для всех ответов: запрет встраивания во фрейм (`X-Frame-Options: DENY` и `frame-ancestors 'none'`), `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` с выключенными камерой, микрофоном и геолокацией. `poweredByHeader: false`.
- Сборка не должна требовать настоящих секретов и данных. Если модуль сессии проверяет `SESSION_SECRET` при импорте, CI передаёт на время сборки заглушку. Код страниц, которому при `next build` нужны данные из базы, не писать: страницы с данными динамические.
- `better-sqlite3` — нативный модуль, он собирается на CI (`ubuntu-latest`, x86-64). Поэтому сервер должен быть тоже Linux x86-64 с не более старой glibc. ARM-сервер потребует ARM-сборщика. Перед переключением релиза `remote-deploy.sh` проверяет, что модуль загружается.

### 2. GitHub Actions (`.github/workflows/deploy.yml`)

**Задание `build`** запускается на каждый push в `main`, на каждый pull request и вручную. Шаги по порядку:

1. Checkout, установка Node из `.nvmrc` с кэшем npm, `npm ci`.
2. `next typegen`: типы маршрутов генерируются при dev или build, в чистом чекауте их нет. Без этого шага проверка типов падает.
3. `tsc --noEmit`, ESLint, `shellcheck deploy/*.sh`, Vitest.
4. Заранее создать пустую базу во временной папке runner'а и включить в ней WAL. Сборка грузит страницы в нескольких воркерах, и на несуществующем файле они иногда ловят «database is locked».
5. `next build` с `NEXT_TELEMETRY_DISABLED=1`, заглушкой `SESSION_SECRET` и `DATABASE_PATH` на базу из шага 4.
6. Упаковка: в `.next/standalone` докладываются `public/`, `.next/static/`, `drizzle/` (миграции), `ecosystem.config.cjs` и `deploy/backup-db.sh`. Из неё удаляются `data/` и любые `.env*`. Всё собирается в `release.tar.gz`.
7. Архив сохраняется как артефакт на 7 дней (кроме pull request).

**Задание `deploy`** идёт после `build` и только при трёх условиях: это push, ветка `main` и переменная репозитория `DEPLOY_ENABLED` равна `true`. Пока сервера нет, работает только `build`.

1. Окружение GitHub `production`; группа очереди `production` без отмены идущего. Два деплоя никогда не идут одновременно, и начатый не обрывается.
2. Checkout только файла `deploy/remote-deploy.sh` (sparse checkout), скачивание артефакта.
3. SSH из секретов: ключ в файл с правами 600, `known_hosts` из секрета, алиас хоста в `~/.ssh/config` с `IdentitiesOnly yes`. Проверку ключа хоста не отключать (никакого `StrictHostKeyChecking=no`).
4. Имя релиза = дата и время UTC + первые 7 символов SHA коммита. Архив и `remote-deploy.sh` копируются по scp в `/tmp` сервера с именем релиза в названии.
5. По SSH запускается скрипт с двумя аргументами (путь к архиву, имя релиза). После этого сам скрипт удаляется из `/tmp`, а код выхода скрипта становится результатом задания.

Секреты окружения `production`: `SSH_HOST`, `SSH_USER` (`deploy`), `SSH_PORT`, `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`. Переменная репозитория: `DEPLOY_ENABLED`. Значения печатает `bootstrap.sh`.

### 3. Выкладка на сервере (`deploy/remote-deploy.sh`)

Аргументы: путь к архиву и имя релиза. Корень — `APP_ROOT`, по умолчанию `/opt/aroma`. Шаги:

1. Прочитать `shared/.env`. Нет файла или не заданы `DATABASE_PATH` / `SESSION_SECRET` — ошибка с подсказкой про DEPLOY.md. `PORT` по умолчанию 3000.
2. Создать недостающие папки. Распаковать архив в `releases/<имя>` (папку предварительно очистить), архив удалить.
3. В папке релиза открыть и закрыть базу в памяти через `better-sqlite3`. Не вышло — нативный модуль не подходит машине, деплой останавливается до переключения.
4. Если база есть — сделать копию `shared/backups/pre-deploy_<релиз>.db` через онлайн-бэкап SQLite (метод `backup` в `better-sqlite3`). **Не** копировать файл через `cp`: в режиме WAL такая копия может оказаться нецелой. Оставить 10 последних таких копий.
5. Запомнить, куда сейчас указывает `current`.
6. Переключить `current` атомарно: создать временный симлинк и переименовать его поверх старого, чтобы не было момента без `current`. Затем `pm2 startOrReload` с конфигом из нового релиза и `--update-env`.
7. Проверка живости: до 30 попыток раз в секунду запросить `http://127.0.0.1:<PORT>/login` и ждать 200.
8. Успех: `pm2 save` (чтобы процесс поднялся после перезагрузки). Удалить релизы старше 5 последних, никогда не трогая активный. Код выхода 0.
9. Неудача: вывести 40 последних строк лога PM2, переключить `current` обратно и перезапустить. Сообщить, что если новая миграция успела примениться, копия базы до деплоя лежит в `shared/backups/`. Код выхода 1, задание красное.

### 4. Запуск под PM2 (`deploy/ecosystem.config.cjs`)

- Имя процесса `aroma`. Рабочая папка и `server.js` указываются через `current`, а не через конкретный релиз.
- Переменные читаются из `shared/.env` флагом Node `--env-file`. Секреты в конфиг и релиз не попадают.
- `NODE_ENV=production` и явно `HOSTNAME=127.0.0.1`. Standalone `server.js` слушает адрес из `HOSTNAME`, а в шелле это имя машины. Без этой строки приложение станет доступно из сети мимо nginx.
- Режим `fork`, один экземпляр. Cluster-режим с SQLite запрещён: несколько процессов будут писать в одну базу и дважды запускать планировщик бэкапов.
- Автоперезапуск: не больше 10 подряд, пауза 3 секунды.

### 5. Что делает приложение при старте (`src/instrumentation.ts`)

Только в среде Node.js и только при `NODE_ENV=production`, по порядку:

1. Применить миграции Drizzle из папки `drizzle/` релиза встроенным migrator'ом `drizzle-orm`. `drizzle-kit` — инструмент разработки, на сервер он не попадает. Таблица учёта миграций та же, что локально, поэтому локально подготовленную базу можно залить на сервер.
2. Если в `users` никого нет — создать владельца `admin` с паролем из `INITIAL_ADMIN_PASSWORD` и пометкой «сменить пароль и настроить 2FA при входе», а также настройки расчёта по умолчанию. Базу с пользователями не трогать. Логика начального заполнения — в одном модуле, общем с локальным `db:seed`.
3. Запустить планировщик бэкапа в S3 (пункт 9).

Правило для миграций: только добавлять (новые таблицы и колонки со значением по умолчанию). Удаление и переименование — в два релиза: сначала код перестаёт использовать поле, потом оно удаляется. Тогда автооткат на предыдущий релиз безопасен.

### 6. Подготовка сервера (`deploy/setup-server.sh`)

Запускается на сервере под root, обычно из `bootstrap.sh`. Входные переменные окружения:

- `DEPLOY_PUBKEY` — публичный ключ CI, обязателен;
- `DOMAIN` — домен; без него сайт работает по http на IP, что годится только для проверки;
- `PROXY` — `direct` или `cloudflare`; если не задан, берётся текущий режим сервера, на новом сервере `direct`;
- `EMAIL` — почта для Let's Encrypt (необязательно);
- `PORT` (3000), `SSH_PORT` (22), `APP_TZ` (часовой пояс магазина);
- `DB_FOLLOWS=1` — базу зальют следом, пароль первого админа не показывать.

Шаги (каждый пропускается, если уже сделан):

1. **Проверки:** запущен под root, есть `apt-get`, есть шаблон nginx, задан ключ, `PROXY` допустимый.
2. **Пакеты:** curl, ca-certificates, gnupg, openssl, sqlite3, ufw, nginx, certbot, fail2ban, cron. Установка без вопросов (`DEBIAN_FRONTEND=noninteractive`).
3. **Node.js 24** из репозитория NodeSource, если стоит версия ниже 22. Не через nvm: nvm не попадает в `PATH` при неинтерактивном `ssh deploy@host "команда"`, и деплой из CI не найдёт `node`. PM2 глобально через npm.
4. **Swap 2 ГБ**, если swap’а нет и памяти меньше 4 ГБ. Запись в `/etc/fstab`. В контейнере ошибка swap — предупреждение, не провал.
5. **Пользователь `deploy`** без пароля. Ключ CI добавляется в `authorized_keys` один раз (права 700 на `.ssh` и 600 на файл). Создать папки из «Раскладки» с владельцем `deploy`.
6. **`shared/.env`** — создаётся, только если его нет. `SESSION_SECRET` — 32 случайных байта в hex, плюс `DATABASE_PATH`, `PHOTOS_DIR`, `PORT`, `APP_TZ`; права 600. Существующий файл не трогать: новый секрет разлогинит всех.
7. **Пароль первого админа.** Если базы нет или в ней нет пользователей, а в `.env` нет `INITIAL_ADMIN_PASSWORD`, — сгенерировать случайные 16 символов и дописать в `.env`.
8. **Автозапуск PM2** через systemd от имени `deploy`, чтобы приложение поднималось после перезагрузки.
9. **Режим доступа nginx** — отдельный файл `/etc/nginx/snippets/aroma-mode.conf`. Первая строка — комментарий с режимом, по нему повторный запуск узнаёт текущий режим.
   - `direct`: переменная схемы равна схеме соединения.
   - `cloudflare`: скачать списки адресов Cloudflare (`cloudflare.com/ips-v4` и `ips-v6`) и проверить, что каждая строка — сеть в формате CIDR. Каждая сеть прописывается как доверенный источник реального IP, сам IP берётся из `CF-Connecting-IP`. Схема — https, если https есть либо в соединении, либо в `X-Forwarded-Proto`. Так работают и Flexible, и Full. Список не скачался: на новом сервере — ошибка, на настроенном — оставить прежний файл.
10. **Конфиг сайта из шаблона** (пункт 7) собирается заново при каждом запуске. Подставляются домен и порт. Пока нет сертификата, строки с пометкой SSL убираются. Перенаправление на https убирается, если нет ни сертификата, ни Cloudflare. Прежний конфиг сохраняется рядом как `.prev`. Сайт по умолчанию отключается. Не прошёл `nginx -t` — вернуть прежний конфиг и остановиться. После reload проверить, что порт 80 отвечает; ответ 502 до первого деплоя — норма.
11. **HTTPS.** Есть домен и нет сертификата — `certbot certonly --webroot` в папку `/var/www/certbot`. После продления запускается `nginx -s reload` (deploy-hook). После успеха конфиг собирается заново уже с SSL и перенаправлением. Режим `certbot --nginx` не использовать: он сам правит конфиг, а у нас конфиг собирается из шаблона. Не вышло — предупреждение «проверьте, что домен смотрит на сервер, и запустите ещё раз».
12. **Firewall (ufw):** входящие только `SSH_PORT`, 80, 443. Правило для SSH добавляется до включения, иначе можно отрезать себе доступ.
13. **fail2ban:** встроенный фильтр `nginx-limit-req` по error-логу nginx: 10 срабатываний за 10 минут → бан на 1 час. В режиме Cloudflare выключен: соединения идут с адресов Cloudflare, и бан в firewall ничего не даст.
14. **Ночной бэкап:** строка в crontab пользователя `deploy`, если её ещё нет. Вызывает `current/deploy/backup-db.sh`, время — 03:30 по времени магазина, переведённое в UTC (сервер живёт в UTC). Вывод — в лог в домашней папке `deploy`.
15. **Итог:** если база новая — показать логин и пароль первого админа. Если приложение уже запущено на пустой базе — перезапустить его, чтобы оно прочитало пароль. Напомнить про секреты GitHub и `DEPLOY_ENABLED`.

Запуск/перезапуск служб: на обычном сервере — через systemd с включением автозапуска, без systemd (Docker-проверка) — через `service`. Простой `reload` недостаточен: остановленную службу он «успешно» не запускает.

### 7. Шаблон nginx (`deploy/nginx.conf.template`)

Файл подключается внутри блока `http` (`sites-enabled`), поэтому `map` и зоны лимитов — на его верхнем уровне. Домен и порт — метки для подстановки. Строки SSL и строка перенаправления помечены комментариями-маркерами, чтобы скрипт мог их вырезать. Содержание:

- Подключение файла режима доступа.
- Перенаправление на https для всего, кроме запросов, уже пришедших по https, и пути проверки Let's Encrypt `/.well-known/acme-challenge/`. Решение принимается по переменной схемы из файла режима, иначе за Cloudflare Flexible получится бесконечный редирект.
- Зоны лимитов по IP. Вход: 6 запросов в минуту, считаются только POST (GET страницы входа не тратит попытки). Остальное: 30 запросов в секунду. Одновременные соединения: 30.
- `upstream` на `127.0.0.1:<PORT>` с keepalive.
- `server`: порт 80, порт 443 с TLS 1.2 и 1.3 и кэшем сессий (строки SSL с маркером), пути к сертификату Let's Encrypt домена. `server_tokens off`. Размер тела запроса — 15 МБ (фото и CSV до 5 МБ с запасом). Превышение лимитов → код 429 с текстом «Слишком много запросов. Подождите минуту и обновите страницу».
- Заголовки к приложению: HTTP/1.1, `Host`, `X-Forwarded-Proto` из переменной схемы. `X-Forwarded-For` и `X-Real-IP` **перезаписываются** адресом клиента, а не дописываются. Иначе клиент подставит чужой IP и обойдёт блокировку входа и журнал. Таймаут ответа 120 секунд: скачивание бэкапа и проверка цен конкурентов идут долго.
- `location`: `/.well-known/acme-challenge/` — файлы из `/var/www/certbot`. `/api/auth/` — зона входа, до 5 сверх лимита без задержки. `/_next/static/` — без лимита. `/` — общая зона, до 200 сверх лимита: одна страница Next делает пачку запросов из-за предзагрузки ссылок.

### 8. Новый сервер одной командой (`deploy/bootstrap.sh`)

Запускается с компьютера разработчика из папки проекта. Параметры: `пользователь@адрес` (обязательно), `--domain`, `--email`, `--cloudflare` или `--direct`, `--with-db`, `-i <ключ>`, `--ssh-port`, `--port`, `--tz`. Без параметров печатает справку.

1. Ключ для GitHub Actions: `~/.ssh/aroma_deploy` (ed25519, без пароля). Создаётся, если его нет.
2. Режим доступа определяется так: флаг → текущий режим с сервера → догадка по заголовку `Server: cloudflare` в ответе домена. В интерактивном терминале скрипт спрашивает, предлагая догадку по умолчанию.
3. Во временную папку на сервере копируются `setup-server.sh` и шаблон nginx, потом запускается настройка с переменными из пункта 6. Переменные кавычатся для шелла. Не root — через sudo с терминалом (`ssh -t`), чтобы sudo мог спросить пароль. Временная папка затем удаляется.
4. `--with-db` — только если на сервере базы ещё нет. Иначе предупреждение «не перезаписываю, там могут быть настоящие данные», и ничего не делается. Локальная база (результат переноса) копируется через `sqlite3 .backup` во временный файл, передаётся и кладётся с владельцем `deploy` и правами 600. Тем же заходом передаётся папка фото.
5. Проверить вход `deploy@сервер` **только** ключом CI (`IdentitiesOnly`), точно как будет заходить GitHub Actions. Напечатать версии node и pm2: заодно видно, что они в `PATH`.
6. Напечатать готовые значения для GitHub: `SSH_HOST`, `SSH_USER`, `SSH_PORT`, путь к приватному ключу, `SSH_KNOWN_HOSTS` (вывод `ssh-keyscan` по хосту и порту), `DEPLOY_ENABLED=true`, адрес сайта. Для Cloudflare — совет включить SSL-режим Full (strict).

### 9. Бэкапы

**Ночной (`deploy/backup-db.sh`).** На входе `DATABASE_PATH` и `BACKUP_DIR`. Нет базы — ошибка. Копия делается через `sqlite3 "<база>" ".backup '<файл>'"`, это безопасно при работающем приложении. Имя файла `aroma_<дата>_<время>.db`. Затем `PRAGMA integrity_check` по копии, удаление копий старше 14 дней и строка в лог.

**Перед деплоем** — см. пункт 3, хранится 10 последних.

**В S3 (из приложения).** Защищает от потери диска VPS: два первых вида бэкапа лежат на том же диске.

- Страница «Настройки → Бэкапы», только для владельца. Поля: endpoint, регион, bucket, ключ доступа, секретный ключ, время ежедневного запуска (по времени магазина), сколько копий хранить. Кнопки «Проверить соединение» и «Сделать сейчас». История запусков: время, размер, результат, текст ошибки.
- Ключи хранятся в базе. В браузер секретный ключ не отдаётся никогда, только последние 4 символа.
- Ход бэкапа: онлайн-копия базы во временный файл → gzip → загрузка через `@aws-sdk/client-s3` с ключом `aroma/db/<дата-время>.db.gz` → удаление копий сверх лимита. Фото догружаются в `aroma/photos/` по имени файла: только новые, уже загруженные не дублируются.
- Планировщик работает внутри процесса и проверяет расписание раз в минуту. Двойной запуск запрещён. Если запуск пропущен из-за перезапуска, он выполняется при следующей проверке в тот же день.
- Ошибка бэкапа показывается владельцу баннером на «Обзоре», пока следующий бэкап не пройдёт.

### 10. DEPLOY.md — что там должно быть

- Быстрый старт: команда `bootstrap.sh`, потом секреты GitHub, `DEPLOY_ENABLED=true` и push в `main`.
- Те же шаги вручную — для понимания и на случай сбоя.
- Ежедневные команды: статус и логи PM2, какой релиз активен.
- **Откат вручную:** переставить симлинк `current` на нужный релиз и сделать `pm2 reload`. Если релиз старше уже применённой миграции: остановить приложение, вернуть базу из `pre-deploy_<релиз>.db`, запустить.
- **Восстановление из бэкапа** (локального и из S3), включая полную потерю сервера: новый VPS → `bootstrap.sh` → база и фото из S3 → деплой.
- Как разбанить свой IP в fail2ban и снять блокировку входа в приложении.
- Что делать, если сайт не открывается: статус nginx → error-лог nginx → запрос к `127.0.0.1:<PORT>/login` с самого сервера. Так видно, кто виноват: nginx или приложение.

### Как проверить деплой до настоящего сервера

Сначала — в контейнере Docker с Ubuntu 24.04 или в локальной виртуалке с SSH, потом на дешёвом тестовом VPS, и только потом на рабочем.

- [ ] Порт приложения (3000) снаружи недоступен
- [ ] Запрос с поддельным `X-Forwarded-For` пишет в журнал настоящий IP

## Перенос данных

Рабочая база переносится одним скриптом `scripts/import-legacy.ts` с последующей сверкой сумм. Старая Арома работает до приёмки новой владельцем, и её база никогда не открывается на запись.

**Эталоны расчётов (до начала переноса логики):**

- В старом репозитории один раз прогоняем функции расчёта (`calculator_v3.quote`, `calculator_quote`, расчёт выпуска, `sales.quote`) на наборе примеров и сохраняем пары «вход → результат» в JSON. Python запускается только в старом репозитории и только для этого; в новом проекте его нет.
- Примеры двух видов. **Синтетические** — не меньше 50 на каждую формулу: все виды доставки, округление вкл/выкл, пустые поля, скидка 0 и 100%, отрицательная цена, нецелые объёмы, ошибки ввода. Они кладутся в `tests/fixtures/` и в Git. **Реальные** — все сохранённые расчёты и документы продаж из копии рабочей базы. В них закупочные цены, поэтому они лежат только локально в `data/` и в Git не попадают.
- Новая реализация считается готовой, только когда совпадает с эталоном на 100% примеров: каждое число и каждый текст ошибки.

**Порядок переноса:**

1. Владелец делает бэкап в старой Ароме (кнопка «Резервная копия») и копирует фото из `static/images/` вместе с `static/image-map.json` рабочей установки.
2. Скрипт создаёт новую базу по миграциям и переносит все таблицы из раздела «Модель данных» с теми же id. Даты переводит в UTC, JSON-снимки не трогает, фото раскладывает в `photos/` и `product_photos`. Все старые записи получают автора «импорт из локальной версии».
3. Скрипт работает в режиме «всё или ничего» и печатает отчёт сверки. Расхождение хотя бы в одной строке — ошибка, новая база не создаётся.
4. Пробный перенос — на тестовый сервер или локально. Владелец сверяет в браузере остатки, несколько документов и итоги продаж со старой Аромой.
5. Переезд: в старой Ароме перестают работать → финальный бэкап → повторный перенос → загрузка на сервер через `bootstrap.sh --with-db` (только на сервер без базы) → проверка в браузере. Старая установка и её база хранятся не меньше месяца.

**Что сверяет отчёт:**

- число строк в каждой таблице;
- суммы `qty`, `remaining`, `total_cost`, `remaining_cost` по всем партиям и по каждому товару;
- для каждой партии: сумма движений равна остатку (количество и стоимость). Несходящиеся партии списком, без исправления;
- итоги каждого документа продаж (выручка, себестоимость, комиссия, наличные, карта) и число версий;
- каждый сохранённый расчёт калькулятора новый код считает так же, как старый (по реальным эталонам);
- фото: сколько перенесено и каких файлов не хватает.

## Производство распивов в складском контуре Next.js

- «Производство» раскрывает боковую панель с выпуском, расчётом, материалами и открытыми флаконами, журналом выпусков. Расчёт использует фактические партии выбранного магазина.
- Одна операция выпуска на 2, 3, 5 или 10 мл. Первый выпуск снимает один закрытый флакон со штучного остатка. Неизрасходованные миллилитры и их стоимость остаются за конкретным открытым флаконом. Каждый готовый распив расходует один атомайзер и одну наклейку. Партии материалов выбираются вручную.
- Программа ищет карточку того же аромата и объёма по названию. При её отсутствии пользователь подтверждает название в предварительном расчёте, карточка создаётся при проведении. Повторный выпуск использует ту же карточку. Вариант аромата (например, EDP или Extrait) сохраняется в названии. Другая партия упаковки меняет себестоимость, а не карточку.
- Владелец исходной партии переходит в партию распива. Себестоимость включает парфюм, атомайзер, наклейку, работу и указанные прочие затраты. Цена продажи задаётся по магазину в остатках. Стоимость исходного флакона сходится до копейки при полном использовании. Расчёт сам по себе движений не создаёт. Проведение проверяет актуальность расчёта и записывает все движения одной транзакцией.
- Источники и выбранные приёмы: [1С:УНФ](https://v8.1c.ru/small.biz/proizvodstvennyy-uchet/) и [МойСклад](https://support.moysklad.ru/hc/ru/производство/процесс%20производства/технологическая_операция) — списание материалов и приход продукции одним документом; [БИФИТ](https://kassa.bifit.com/wiki/index.php?title=Калькуляционная_карта) — складские партии комплектующих; [Эвотор](https://evotor.ru/tovarysklad/uchet-ostatkov/uchet-ostatkov-na-proizvodstve/) — предварительный расчёт, проведение выпуска и дальнейшая продажа готовой позиции.

### Магазин назначения при выпуске

В форме выбираются склад материалов и магазин назначения. Один документ списывает материалы со склада производства и приходует весь готовый выпуск в выбранный магазин. Открытый флакон остаётся за складом материалов. По умолчанию магазин назначения совпадает со складом материалов. В журнале видны оба магазина, старые выпуски считаются выпущенными на исходный склад. За основу взят выбор склада материалов и склада продукции в [техоперации МоегоСклада](https://support.moysklad.ru/hc/ru/производство/процесс%20производства/технологическая_операция).

### Действия каталога

Панель категории содержит создание товара, импорт, экспорт и удаление выбранных карточек из списка. Импорт и экспорт вынесены в панель по образцу [БИФИТ](https://kassa.bifit.com/news/kejsyi/import-export-spravochnika-tovarov). Импорт в конкретной категории назначает её новым карточкам, экспорт сохраняет карточки всей категории. Удаление скрывает карточку из каталога с сохранением истории, а позиции с остатком защищены. Создание и открытие карточки используют одну форму, включая выбор фото. При переходе на другую страницу список прокручивается вверх. Существующие карточки «Объёмов» перенесены в «Полноразмерные флаконы».
